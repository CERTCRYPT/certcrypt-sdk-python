## 1.0.0

* feature:Settlement: `build_verification_package()` requires `base_certificate`; every package carries it with `verification_context` (verification-package/1), which is what an offline verifier in package mode accepts
* feature:Consistency: `assemble_context_snapshot_certificate` mints a CCVP/1 context snapshot certificate (`payload.snapshot` plus one `subject.context-snapshot/1` subject committing to it, shape and profile preconditions checked before signing); `assemble_base_certificate` takes an optional `context` (the snapshot issuer by `signer.id` and composite key fingerprint, and the `context_set_id`); `issuer_key_fingerprint_hex` gives that fingerprint. Held to the `ccvp-consistency` vectors
* feature:Formats: lowercase-hex and timestamp checks match the whole string; a trailing newline is refused
* security:Issuance: `subject.ai-decision/1` accepts one bounded decision record with a canonical decision id, one declared model, an explicit client/runtime observation boundary, real UTC millisecond timestamps, and ordered multimodal input/output parts; every part has a globally unique id and nonce, a lowercase MIME essence, an admitted profile and a salted CCCP commitment, while parameters and context remain bounded flat string maps
* feature:Issuance: `build_ai_decision_subject` generates independent part nonces, computes profile-aware commitments, validates the complete decision record and returns the subject plus private opening material; `build_ai_decision_part` provides the same operation for one part
* security:Issuance: the material of the JSON subject profiles (`subject.collection/1`, `subject.ai-decision/1`, `subject.context-snapshot/1`) is parsed strictly (`certcrypt.crypto.strict_json`): a member name repeated in any object, at any depth and after escape decoding, refuses the subject before it is canonicalized, and so do `NaN`, `Infinity` and a leading byte-order mark. Held to the new conformance family `strict-json`
* security:Node authentication: the issuer proof signs `certcrypt:issuer-auth:1|<challenge>|<host>|<METHOD> <path?query>|<sha3-256 of the body>` (`issuer_auth_message`), so a copy is good only for repeating that very request. The client's `issuer_auth_proof` provider receives the request (method, url, body)
* feature:Retries: every attempt of `issue()` and of a read carries a newly minted issuer proof, because the node refuses a challenge it has already accepted; a retry of a request that reached the node is therefore never refused as a replay
* security:Issuance: the issuer's signing key depends on the seed alone — P-256 from `SHA3-256(seed || "issuer-cert-key/p256")`, ML-DSA-65 from `SHA3-256(seed || "issuer-cert-key/mldsa")`; `issuer_key_id` is a label that never changes the key, and its default is `"issuer:" + keyset_root[0:32]`. Held to the new conformance family `issuer-key-derivation`
* feature:Exports: `ZERO_DATA_PROFILE`, `COMMITMENT_LEAF_VERSION`, `PROFILE_P256_MLDSA65`, `COLLECTION_MERKLE_SCHEME`, `SUBJECT_CONTEXT_SNAPSHOT`, `SettlementProgress`, `BuiltCollection` and `ResolvedCollection`; `SUPPORTED_SUBJECT_PROFILES` lists `subject.context-snapshot/1`, which this SDK implements
* feature:Issuance: `mode="unlinkable"` with a `tree_size` below 2 is refused at construction (`unlinkable mode needs a treeSize >= 2 (a distinct leaf per cert)`), and so is a `commitment_ttl_seconds` that is not a positive whole number of seconds
* feature:Issuance: `Certcrypt` takes `retry_base_ms` and `retry_cap_ms` alongside `retry_max_elapsed_ms` and `retry_max_attempts`
* feature:Issuance: `resolve_emission()` takes an optional `verification_context`, defaulting to the instance's `rules_version` and `system_id`. It reads the operation once and waits only when asked (`max_attempts` above 1, `max_wait_ms` or `strategy="auto"`); a wait that ends without a terminal state resolves as `pending`. Every terminal state other than `independent_ready` and `expired` resolves as `rejected`, on the by-commitment fallback too
* feature:Issuance: `EmissionHandle.from_dict()` requires `commitment_index`; it never defaults a missing one to 0, which would yield an inclusion proof that verifies against nothing
* docs:Issuance: `prepare()` checks, in order: activation, pool, holder, root fingerprint, system id, subjects, subject profiles, then TTL. An optional value falls back only when absent (`None`): an explicit `0` or empty string is used as given
* feature:Settlement: `wait_for_operation()` raises `CertcryptNodeError` (`operation <id> did not reach a terminal state after <n>s (last state: <state>)`, plus the window when one was reported) when the wait ends without a terminal state, `build_verification_package()` raises the same way
* feature:Settlement: `wait_for_operation()` takes `max_attempts` and `strategy` (`"auto"` or `"fixed"`); `interval_ms` or `max_attempts` selects `"fixed"` (default 60 polls at 1 s) and `"auto"` is bounded by `max_wait_ms` (default 15 minutes). It runs on the client's clock (`now_ms` and `sleep` on `CertcryptNodeClient`)
* feature:Settlement: `OperationRecord.settlement_progress` and `WaitProgress.settlement` (`SettlementProgress`: `phase`, `progress_ppm`, `observed_at`, and nothing else from the wire), and `WaitProgress.message` names the real wait — the window, an overdue window, or on-chain irreversibility with its percentage
* feature:Settlement: an exception raised by `on_progress` is swallowed, and without `on_progress` a sleep of ten seconds or more, or an overdue window, is logged at INFO on the `certcrypt` logger
* feature:Settlement: `SettlementWindowEstimate.expected_settled_by` (and `UnresolvedEmission.expected_settled_by`) carry the operator's estimate of when the window's settlement is anchored and final — never earlier than `target_close_by`, present exactly when it is, operational only. `wait_for_operation()` checks twice before `overdue`: 60 % of the way from `target_close_by` to that instant, then at that instant plus one second, each pushed back by a random 0–1 s so the operations of one window do not ask at once; `overdue` (on `WaitProgress` and on a `pending` resolution) is true only once it has passed; the progress message names the expected instant, and an overdue one says settlement is past the operator's expected instant. Without it, the wait sleeps until `target_close_by` plus three seconds and `overdue` follows `target_close_by`
* feature:Settlement: a window `target_close_by` or `expected_settled_by` with fractional seconds (`…:00.000Z`) or an offset is read as an instant
* feature:Node client: `health()` is one request bounded at 30 seconds that reports `False` on a transport failure or a non-2xx status
* security:Activation: an activation answer is read fail-closed, in order: not a JSON object (`activate returned no JSON object`), a required field absent or empty (`activate returned no …`), a field of the wrong type — `level1_binding` not an object, `level1_signature` not a composite signature, `holder_id`/`pool_id` not strings (`activate returned a malformed …`), or a `status` other than `redeemed`/`already_consumed_same_root` (`activate returned an unrecognized status`). Each raises `CertcryptNodeError` with no HTTP status, and nothing is cached or persisted.
* feature:Node auth: The node is a transport. The SDK activates and submits through it and asks it for nothing else — no identity proof, no pinned key. A node that is not recognized gets nothing admitted, and one that misbehaves can delay or drop a submission but never forge or alter what is signed: the certificate is signed here, and the `Proof of Independence` that comes back is signed by the CERTCRYPT System Domain, which any verifier checks offline with the verifier toolkit
* feature:Activation: `activate()` sends the request `POST /v1/activate` accepts — the activation `code`, the key-set root, a leaf disclosure with its ML-DSA-65 possession signature over `certcrypt:activate:1|<code>|<root>`, `rules_version`, `system_root_fingerprint` and a validity window stable across restarts — and reads `level1_binding`/`level1_signature`, `holder_id` and `pool_id` from the answer. `already_consumed_same_root` is a success, `integration_key_replaced` and `key_set_root_already_bound` surface on `CertcryptNodeError.code` without a retry, and `CertcryptNodeClient.activate()` returns an `ActivationResult`. `valid_until` sets the end of the window; its start is fixed by the issuance service
* security:Issuance: the issuer authenticates every request to the node (`x-certcrypt-issuer-auth`, a fresh self-verifying proof) and signs every read (`x-certcrypt-issuer-read`) over the id the server routes on. A member the node delivered late is learned from the first read that shows its upstream id; a restored handle registers its own
* feature:Node client: `pre_evaluation_rejected` is final and not retried — the node sends it with HTTP 200 and the same set always gets the same answer
* feature:Issuance: `Certcrypt.issue()` — the single issuance surface: derives the signing key from your seed, canonicalizes each subject byte-identically to the verifier, computes the commitment, mints the signed base certificate and submits the issuance
* feature:Issuance: No opaque-digest mode — a certificate always commits to real content, so a third party can bind the proof to those exact bytes
* feature:Issuance: Multi-subject certificates under one signature; order is significant and `subjects[0]` is the primary face
* feature:Issuance: Six subject profiles — `subject.binary/1`, `subject.text/1` (line-ending normalized), `subject.email/1` (RFC 5322 header-unfolded), `subject.collection/1` and `subject.ai-decision/1` (canonicalized by value under RFC 8785 after a string-only precondition), and `subject.context-snapshot/1` (canonicalized by value, no JSON number at any depth)
* feature:`EmissionHandle`: A serializable operation handle — persist it and `resolve_emission()` finishes the job after a restart or in another process, without re-emitting; exactly one node operation per certificate
* feature:Issuance: Explicit failure where a silent default would mint a rejected certificate — an unknown `rules_version` without an explicit TTL raises rather than defaulting to a far-future expiry, and an empty `system_id` raises rather than producing a certificate every conformant verifier refuses
* feature:Cryptography: Composite PQ/T signatures — ECDSA-P-256-SHA3-256 (classical, first; order is load-bearing) AND ML-DSA-65 (FIPS 204), each over the same domain-separated message, valid only as the AND of all components
* feature:Cryptography: ECDSA signatures are RFC 6979 deterministic — SHA3-256 prehash, nonce from HMAC-SHA3-256, low-s, raw `r||s` — so the same key over the same message always yields the same signature, held to the conformance family `ecdsa-p256-deterministic`; a random-nonce signature over the same message is equally valid and each verifies under the other. The ML-DSA-65 component stays hedged
* feature:Cryptography: The signing key never leaves the process — derived deterministically from the 32-byte seed you provision
* feature:Cryptography: No API signs a single component, so there is no way to produce something that looks like a signature but carries no post-quantum half
* feature:Byte contracts: SHA3-256 from the standard library (FIPS 202, not Keccak) and RFC 8785 JCS, with the three places Python's `json` diverges from RFC 8785 handled explicitly — UTF-16 code-unit key ordering, ECMAScript number serialization, and non-ASCII staying literal
* feature:Byte contracts: Two constructions deliberately break the "canonical means JCS" rule and are pinned by tests — the commitment leaf preimage and the projected commitment serialize in INSERTION order
* feature:Byte contracts: The collection fold and the holder-keyset Merkle are separate modules — different constructions over the same digest (ASCII tags with length prefixes versus `0x00`/`0x01` discriminators), and swapping them produces a root wrong in a way no length check catches
* feature:Zero-data: The issuer's stable identifiers are projected to operation-scoped pseudonyms and never appear in the capacity evidence; a test serializes the whole evidence and asserts none of them appears
* feature:Zero-data: Per-operation leaf keys from a Merkle tree derived from the master seed, so two commitments from the same issuer share only the root; `mode="unlinkable"` requires a `LeafStore` at construction rather than defaulting to something that silently reuses a leaf
* feature:Node client: Standard library only (`urllib`), so the SDK carries no HTTP dependency; a transport can be injected for callers who prefer `requests` or `httpx`
* feature:Node client: Submission sets bounded at 64 members (`MAX_SUBMISSION_SET_MEMBERS`). `Certcrypt.submit()` and `CertcryptNodeClient.issue()` refuse more than 64 commitments with `SubmissionSetTooLargeError` before anything is sent; `assert_submission_set_within_bound()` is exported for a caller that groups commitments itself. A fail-fast guard, not a security boundary: the node and the submit endpoint reject an over-cardinality set fail-closed regardless
* feature:Node client: Idempotent retries with exponential backoff and full jitter; `issue()` fixes a ULID `request_id` once and resends the same signed set under it, so a retry never re-signs and never double-submits; terminal verdicts fail fast
* feature:Node client: Retries follow the `transport-retry` policy — a node's `Retry-After` (a restart, an outbox it cannot write) is waited out exactly, clamped to 1 s – 15 min, and never counted as an attempt; retrying ends on a time budget (`retry_max_elapsed_ms`, default 120 s) with no attempt limit unless `retry_max_attempts` is set; a 4xx other than 408/425/429 is raised at once instead of retried. `CertcryptNodeError.retry_after_ms` carries the node's requested wait when the client gives up
* feature:Node client: `list_dead_letters()` and `redrive_dead_letter(request_id)` — the submissions the node stopped retrying (a refusal about the request or its credentials, never an outage) and how to put one back once the cause is fixed; the same signed set is resent, nothing re-signed
* feature:Node client: A member the node delivered late (`accepted_for_retry` at submit) keeps the operation id it was given; the first read that reveals its upstream id hands it to `on_upstream_operation_id`
* feature:Node client: Waiting is scheduled, not spun — the client sleeps until the settlement window the node reports instead of polling, and says when an operation is running late
* feature:Node client: `accepted_for_retry` is not terminal; the node has durable custody and will deliver
* feature:Conformance: Validates against the published vectors in `certcrypt-conformance`, which are NOT vendored — the contract is versioned separately and a copy would drift; tests fail with a message naming what to check out when the sibling is absent (`CERTCRYPT_ALLOW_MISSING_CONFORMANCE=1` turns those failures into skips)
* feature:Conformance: Certificates minted here are round-tripped through `certcrypt-verifier-toolkit-js`, which verifies both composite components on every run
* feature:Packaging: Requires Python 3.10 or newer, Apache-2.0. Server-side only — the issuer seed must never reach a client device
